## 2. 盘点结论

- 当前 Java 完整计划最多包含 29 个步骤：15 个 Kubernetes 基础步骤，以及按配置启用的 14 个 Kubemate 公共/组件步骤。
- 15 个基础步骤中，14 个安装步骤已有内联 `verifyCommand`，最终集群健康检查为内置验证动作。
- `scripts/verify/phase2_k8s_base/` 中存在对应历史脚本，但多数仍依赖 `PROJECT_ROOT`、`config.sh`、`ssh.sh` 和嵌套 SSH，不能直接作为 v0.3.2 逐节点前置验证脚本。
- Kubemate 当前计划中的 5 个安装步骤缺少同键验证脚本；公共 Helm 步骤也缺少同键验证脚本。
- 组件步骤当前未绑定独立验证脚本，必须在双重验证执行引擎接入前补齐或迁移。

## 5. 历史 verify 风险清单

### 5.1 嵌套 SSH

以下当前计划相关脚本明确调用 `ssh_exec_capture` 或直接 SSH，必须迁移为“在当前目标节点执行”：

- `verify-11b-setup-hostname.sh`
- `verify-12-setup-k8s-repo.sh`
- `verify-13-install-k8s-deps.sh`
- `verify-14-replace-kubeadm.sh`
- `verify-15-environment-config.sh`
- `verify-16-install-containerd.sh`
- `verify-17-install-registry.sh`
- `verify-18-init-k8s-cluster.sh`
- `verify-19-modify-cert-expiry.sh`
- `verify-20-add-control-nodes.sh`
- `verify-21-add-worker-nodes.sh`
- `verify-22-install-cni-flannel.sh`

### 5.2 控制端配置依赖

多项脚本读取 `PROJECT_ROOT`、`cluster.yaml`、`config.sh` 或控制端公共库。v0.3.2 统一改为只读取远端任务目录中的 `runtime.env` 白名单变量和必要只读公共函数。

### 5.3 超时与退出码

- 现有多数 `systemctl`、`kubectl`、`helm` 和网络检查没有统一外层超时。
- 历史脚本主要使用普通成功/失败退出码，尚不能区分 `0=已满足`、`10=未满足`、`20=验证异常`、`21=验证超时`。
- 迁移时不得把 SSH 不可达、权限不足、Kubernetes API 不可用误判为“目标未满足”。

### 5.4 敏感信息

- 集群初始化、控制节点加入和 Worker 加入验证不得输出 Join Token、证书 Key、完整 Join 命令或 kubeconfig。
- Redis、MinIO 及其他组件验证不得输出 Secret 内容或带密码的命令。

## 6. 实施顺序

1. 先为 `InstallStep` 增加显式验证脚本和步骤类型字段，并在计划构建时校验完整性。
2. 优先迁移 Registry、集群初始化、控制节点加入和 Worker 加入四个关键步骤。
3. 补齐 6 个缺少同键 verify 的公共/组件步骤。
4. 迁移其余基础和组件验证脚本，完成 100% 覆盖后再启用双重验证执行引擎。
