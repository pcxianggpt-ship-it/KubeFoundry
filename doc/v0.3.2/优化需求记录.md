## 3. 待办需求清单

### 3.1 安装进度阶段任务分组展示

- 当前情况：正式安装页面和安装进度页面直接展示三十多项阶段任务，信息层级较多，用户难以快速理解整体安装进度。
- 目标：将阶段任务按部署组件或业务域进行分组展示，以减少页面的视觉混乱，并让用户先看到整体阶段，再查看阶段内的具体任务。
- 分组方向：同一组件的相关任务归入同一部署阶段。例如，“配置 NFS exports”和“工作节点挂载 NFS”均归入“部署 NFS 组件”阶段。
- 预期体验：页面应能清晰区分组件级阶段与阶段内任务，并正确反映每个阶段及其任务的执行进度、状态和失败信息。
- 待后续确认：完整的分组目录、各现有任务的归属、组级状态计算规则、展开/收起交互及历史任务展示兼容方式，均在设计阶段确定。

### 3.2 Kubemate MinIO 配置参数

- 目标：在“集群配置”的 Kubemate 组件页面中，为 MinIO 增加可配置的部署参数。
- 参数范围：至少包括 PVC 容量、CPU 分配和内存分配等资源相关参数。
- 安装条件：MinIO 至少需要 4 个工作节点。允许用户先保存 MinIO 组件配置；开始安装时，根据集群配置中的正式工作节点数量统一执行准入校验，少于 4 个时不得开始安装。
- 校验要求：只统计当前集群配置中 `is_draft=false` 且角色包含 `worker` 的正式节点；不要求为 3 Worker 和 4 Worker 分别准备独立验证环境，也不增加“至少 4 个 Worker 为 Ready”的专项校验。
- 预期体验：用户可在 MinIO 组件配置区域填写或调整上述参数，并在后续安装时使用对应配置。
- 验收方向：通过集群配置数据验证边界；3 个及以下正式工作节点且启用 MinIO 时，安装开始即被拒绝，恰好 4 个及以上时可进入安装。安装阶段仍验证 MinIO Tenant、Pod 和 PVC 的通用就绪状态，但不单独校验 Ready Worker 数量。
- 待后续确认：参数的完整清单、默认值、单位与输入校验规则，以及 CPU 和内存是否分别支持 requests 与 limits，均在设计阶段确定。

### 3.3 etcd 备份单元

- 目标：在全部安装任务完成后，新增 etcd 备份单元作为安装流程的最后一个执行单元。
- 执行顺序：该单元应位于所有现有安装任务之后执行。
- 预期体验：安装进度页面应展示 etcd 备份单元的独立执行状态、进度、日志和失败信息。
- 待后续确认：备份触发方式、备份内容与保留策略、存储位置、失败后的整体任务状态和恢复验证方式，均在设计阶段确定。

### 3.4 本地 YUM 仓库 HTTP 访问权限修复

- 当前情况：管理节点将本地 YUM 仓库发布在 `/var/www/html/repo` 后，部分环境执行 `yum makecache` 请求 `http://k8sc1/repo/repodata/repomd.xml` 返回 HTTP 403。
- 已确认原因：`httpd` 服务账户对 `/var/www` 路径中的某一级目录缺少搜索（目录执行）权限，无法进入 `/var/www/html` 读取仓库元数据；服务端日志显示 `search permissions are missing on a component of the path`。
- 目标：安装流程应确保 HTTP 服务账户能够遍历仓库目录并读取仓库元数据，使所有节点能够通过 HTTP 正常执行 `yum makecache`。
- 验收要求：在仓库节点本机及任一远程节点访问 `http://k8sc1/repo/repodata/repomd.xml` 均返回 HTTP 200；所有节点执行 `yum makecache` 成功，且不再出现 HTTP 403。
- 最终要求：由 root 将 `/var/www`、`/var/www/html` 和仓库内容设置为 `777`，直接停止并禁用 firewalld；实现保持简单，不增加 ACL、`policycoreutils` 或其他 SELinux 管理工具依赖。

### 3.5 确认集群安装范围时展示节点 IP

- 当前情况：确认集群安装范围时展示的节点清单未明确显示节点 IP，无法便捷核对实际安装目标。
- 目标：在确认集群安装范围的节点清单中显示每个节点的 IP 地址。
- 预期体验：用户在发起安装前可通过节点名称、角色及 IP 地址核对所有目标节点，避免安装到错误节点。
- 待后续确认：IP 地址的展示位置、缺失或非法 IP 的提示方式，以及与节点编辑页面数据的一致性校验，在设计阶段确定。

### 3.6 重置流程移除 Helm 前置依赖

- 当前情况：集群重置的第一个任务要求使用 Helm；当安装在第二阶段失败时，集群可能尚未安装 Helm，导致重置流程无法合理执行。
- 目标：调整重置流程，使其不以已安装 Helm 作为第一个任务的前置条件。
- 适用场景：安装流程在 Helm 安装前或 Helm 未完成可用时失败，仍应能够发起集群重置。
- 预期体验：重置流程可根据当前集群实际安装状态安全执行，并明确显示不依赖 Helm 的初始清理任务及其执行结果。
- 待后续确认：各重置任务的实际依赖关系、无 Helm 场景下的执行顺序、幂等性及失败处理策略，在设计阶段确定。

### 3.7 重置时清理工具新增的参数配置

- 目标：执行集群重置时，应一并清理由 KubeFoundry 工具添加或写入的参数配置。
- 范围：覆盖安装或配置过程中由工具管理的相关参数，避免重置后遗留配置影响后续安装或节点使用。
- 预期体验：重置完成后，工具写入的参数配置不再保留；清理结果应可在任务状态、日志或验证结果中确认。
- 待后续确认：需清理的参数配置完整清单、配置文件或系统位置、用户原有配置的保护边界、备份/恢复策略及清理失败处理方式，在设计阶段确定。

### 3.8 Redis Sentinel 模式部署与离线安装文件

- 目标：支持 Redis Sentinel（哨兵）模式的自动化部署。
- 参考实现：后续设计和实现参考 [Bitnami Redis Helm Chart](https://artifacthub.io/packages/helm/bitnami/redis)，并以该 Chart 在实施时的受支持参数为准。
- 离线介质：将 Redis 安装所需的离线 Helm 文件及相关安装文件补充至 `kube-media/03.setup_file/v1.30.14/helmapp/redis/` 目录。
- 预期体验：用户启用 Redis 组件后，可在离线环境中完成 Sentinel 模式部署，并获得明确的主节点、副本节点和 Sentinel 服务就绪状态。
- 待后续确认：Chart 版本、离线镜像及 Helm 依赖物清单、Sentinel/副本数量、认证与密码管理、持久化配置、资源参数、服务暴露方式、故障切换及验收标准，均在设计阶段确定。

### 3.9 安装任务失败重跑与续跑

- 当前情况：安装任务中途失败后，缺少基于实际安装状态继续执行或安全重跑的能力，可能重复执行已经正常完成的步骤。
- 目标：为安装任务增加失败重跑或续跑功能，通过步骤验证结果判断是否需要再次执行。
- 执行前验证：进入每个安装步骤时，先执行该步骤在 `verify/` 目录中对应的验证脚本；若验证通过，说明该步骤已正常完成，应跳过安装操作，并将步骤明确标记为“已验证并跳过”或等价状态。
- 步骤执行：若执行前验证未通过，则正常执行该步骤的安装操作；验证未通过仅表示该步骤尚未达到目标状态，不应直接终止整个续跑流程。
- 执行后验证：步骤安装操作完成后，必须再次执行对应的验证脚本；验证通过后才可将该步骤标记为成功，验证未通过则将步骤标记为失败并保留可诊断信息。
- 示例：进入镜像仓库安装步骤时，若验证脚本确认镜像仓库已经正确安装且可用，则跳过镜像仓库安装操作并继续后续步骤。
- 验证脚本优化：现有 `verify/` 脚本如不能准确、幂等地判断目标状态，可在实施阶段同步优化，并补充缺失步骤的验证脚本。
- 预期体验：用户可对失败任务发起重跑或续跑；已完成且验证通过的步骤不会重复执行，未完成或验证失败的步骤继续执行，页面能够区分成功、失败、执行中和已验证跳过状态。
- 待后续确认：重跑与续跑的入口、任务 ID 和历史记录关系、起始步骤选择、验证超时与重试规则、验证脚本异常和目标未就绪的区分方式，以及跳过状态的进度计算规则，均在设计阶段确定。
