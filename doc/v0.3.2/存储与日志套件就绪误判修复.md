# KubeFoundry v0.3.2 存储与日志套件就绪误判修复

## 1. 问题与验证范围

2026-10-08 收到反馈：内网开发集群部署“存储与日志套件”时提示工作负载未就绪，但 Pod 已启动。现场当前无法连接，因此尚未确认实际失败的是 Loki 还是 Alloy，也未读取现场任务日志。

本地检查发现 `35-install-loki.sh` 和 `48-install-alloy.sh` 均启用 `pipefail`，并通过 `kubectl get pods | grep -q` 检查 Pod 名称。在匹配项位于较长列表开头时，`grep -q` 提前退出；上游仍在输出的 `kubectl` 可能收到 SIGPIPE，导致管道返回非零，从而误报“工作负载未就绪”。

本地 Linux 复现：匹配 Pod 为 Running，后面追加 4000 条无关 Pod 记录。原检查管道返回 `141`；读取完整输出后返回 `0`。新增回归用例在修复前能触发 `Loki 工作负载未就绪`，与反馈现象一致。此证据确认代码存在误判缺陷，不能替代现场根因确认。

## 2. 修复内容

- 两个安装脚本改用 `grep loki >/dev/null`、`grep alloy >/dev/null`，完整消费 Pod 查询结果，避免提前关闭管道。
- 保留 `pipefail`：即使输出中有匹配 Pod，查询命令返回失败仍拒绝成功；没有对应 Pod 时也仍报错。
- 保留 Helm 的 `--wait` 及已有 rollout 等待；本次仅修复检查管道，不调整工作负载就绪标准。

涉及文件：

- `scripts/steps/phase3_ecosystem/35-install-loki.sh`
- `scripts/steps/phase3_ecosystem/48-install-alloy.sh`
- `scripts/tests/test_phase3_storage_observability.sh`

WSL Linux 中的两项回归测试及修改脚本的 Bash 语法检查已通过。回归测试覆盖 Loki、Alloy 的长列表误判、对应 Pod 缺失、查询失败但包含匹配输出，以及原有 MinIO/OpenEBS 安装行为。
