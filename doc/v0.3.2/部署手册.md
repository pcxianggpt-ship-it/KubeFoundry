# KubeFoundry v0.3.2 部署手册

## 1. 交付物

v0.3.2 的 Web 发布包和 Kubernetes 离线介质是两个独立交付物：

- Web 发布包：`kubefoundry-web-v0.3.2-{x86_64|aarch64}.tar.gz`，包含 Java 17 精简运行时、后端、前端、Helm、安装/验证/验收脚本和模板。
- 离线介质：部署目录中的 `kube-media/`，包含 RPM、Kubernetes 文件、Chart、组件 YAML 和私有镜像仓库包；Web 发布包不会携带或覆盖该目录。

生产部署前必须核对两者均来自同一个 v0.3.2 冻结基线，并验证各自的 SHA-256。

## 2. 环境要求

- 目标管理服务器为 Linux `x86_64` 或 `aarch64`，使用匹配架构的发布包。
- 使用 root 部署 systemd 服务；默认端口为 `10001`。
- 管理服务器能够通过 SSH 访问所有目标节点，并能访问独立 `kube-media/`。
- 目标 Kubernetes 版本为 `v1.30.14`；离线介质必须包含当前计划启用组件所需内容。
- 启用 MinIO 时，集群配置至少包含 4 个非草稿 Worker；这不是 Ready 状态门禁。

## 3. 构建发布包

### 3.1 x86_64 构建

```bash
export KF_JAVA_HOME=/opt/jdk-17.0.17
export KF_TARGET_ARCH=x86_64
bash package.sh
sha256sum dist/kubefoundry-web-v0.3.2-x86_64.tar.gz
```

正式构建会运行后端和前端测试，并通过 `jlink` 生成目标架构运行时；测试模式产物不能用于生产。

### 3.2 WSL 交叉构建 ARM64

x86_64 构建机使用宿主 JDK 17 运行 Java 和 `jlink`，目标模块必须来自真实 ARM64 JDK 17。目标 JDK 选择顺序为：显式 `KF_TARGET_JDK_HOME` 优先；未指定时，ARM64 交叉构建使用 `KF_ARM_JAVA_HOME`；其余情况使用宿主 JDK。脚本继续检查目标 Java 启动器和生成运行时的实际架构，不能把 x86 运行时标记成 ARM64。

当前 WSL 的 `/etc/profile.d/kubefoundry-arm-jdk.sh` 已配置 `KF_ARM_JAVA_HOME=/opt/jdk-17.0.17-aarch64`。在加载该配置的 WSL 登录 Shell 中执行：

```bash
KF_TARGET_ARCH=aarch64 KF_JAVA_HOME=/opt/jdk-17.0.17 bash package.sh
```

未加载登录 Shell 配置时，可直接显式指定目标 JDK：

```bash
KF_TARGET_ARCH=aarch64 KF_JAVA_HOME=/opt/jdk-17.0.17 \
  KF_TARGET_JDK_HOME=/opt/jdk-17.0.17-aarch64 bash package.sh
```

2026-10-08 修复了 `package.sh` 将未指定的目标 JDK 强制回退到宿主 JDK、忽略已有 `KF_ARM_JAVA_HOME` 的问题。目标 JDK 选择回归测试为 `scripts/tests/test_jre_target_jdk.sh`。已在 x86_64 WSL 完成实际 ARM64 打包，后端测试、前端 105 项测试和构建通过，包内 182 项文件校验和通过，Java/JVM/Helm ELF 均为 aarch64；真实 ARM64 Linux 主机运行验收仍需单独完成。

## 4. 首次部署或升级

在目标安装目录放置发布包、`deploy.sh` 和已经准备好的 `kube-media/`：

```bash
sudo bash deploy.sh kubefoundry-web-v0.3.2-x86_64.tar.gz
```

指定端口：

```bash
sudo bash deploy.sh --port 10001 kubefoundry-web-v0.3.2-x86_64.tar.gz
```

部署脚本会验证压缩包路径、符号链接、必需文件、包架构和运行时架构。自 2026-10-08 起，`deploy.sh` 不再执行发布包内部的 `sha256sum -c SHA256SUMS`，也不要求部署环境提供 `sha256sum` 或发布包包含 `SHA256SUMS`；文件内容变化后不会因“发布包文件校验失败”中止部署。打包脚本仍生成校验和文件，供交付时手动核对。

升级会替换 `app/`、`scripts/`、`tools/` 和 `templates/`，保留：

- `data/`：H2 数据、主密钥、任务和凭据密文；
- `logs/`：服务与部署日志；
- `kube-media/`：离线介质。

## 5. 服务操作

```bash
sudo bash deploy.sh --status
sudo bash deploy.sh --restart
sudo bash deploy.sh --stop
sudo bash deploy.sh --uninstall
```

`--uninstall` 只删除并停止 `kubefoundry-web.service`，保留程序、数据、日志和脚本。需要彻底删除数据时必须另行确认目标路径，不能把卸载命令当作数据清理命令。

## 6. 部署后检查

```bash
systemctl status kubefoundry-web --no-pager
curl --fail http://127.0.0.1:10001/api/health
```

浏览器访问 `http://<管理服务器IP>:10001`。确认 `/cluster-config` 和 `/cluster-install` 深层路由可刷新，并检查部署目录权限：`data/`、`logs/` 应为 `0700`。

## 7. 回滚边界

部署前备份 `data/` 和当前发布包。Flyway V15 完成后，不允许通过替换旧 JAR 直接降级数据库；需要回退时应恢复与旧版本配套的完整数据备份。不得把 `doc/server.md`、节点明文密码、私钥或验收日志打入发布包。
