## 3. 需求清单

### 3.1 CoreDNS 副本反亲和性配置

- 触发时机：Kubernetes 集群初始化完成后，作为 Kubernetes 底座安装流程的一项后续任务执行。
- 目标：为 CoreDNS 增加 Pod 反亲和性（anti-affinity）配置，使多个 CoreDNS 副本尽量调度到不同节点，降低单节点故障导致 DNS 服务副本同时不可用的风险。
- 范围归属：Kubernetes 底座安装，不属于 Kubemate 组件。
- 实施要求：后续设计时应明确配置应用方式、幂等策略、适用 Kubernetes 版本、单节点集群的降级行为，以及 Deployment 就绪和 Pod 分布的验证方式。
- 验收方向：多节点集群中，CoreDNS 可用副本应优先分布在不同节点；节点资源不足或节点数量不足时，不应因该策略导致 DNS 工作负载永久不可调度。

### 3.2 MinIO 自动化部署

- 当前情况：MinIO 通过 MinIO Operator 的 Console 进行安装，仍需人工介入。
- 目标：调研并实现可通过命令或脚本完成的 MinIO 部署方式，消除 Console 人工操作。
- 范围归属：Kubemate 的存储与日志原子组件组，需与 OpenEBS、Loki、Alloy 的既有依赖顺序保持一致。
- 调研要求：比较 Operator CR、Helm Chart 或其他受支持的非交互部署方式，确认离线介质、凭据安全、幂等执行、就绪等待、失败重试和升级兼容性。
- 实施要求：选定方案后，部署过程不得要求浏览器或 Console 人工确认；敏感信息不得输出到日志、任务快照或接口响应。
- 验收方向：在无人值守条件下完成 Operator（如仍需要）和 MinIO Tenant/工作负载部署，并验证工作负载就绪、服务可访问、持久化存储绑定及供 Loki 使用的最小对象存储链路。

### 3.3 集群配置服务器节点管理优化

- 当前情况：集群配置的服务器节点页面需要逐个发起连通性测试，且新增或编辑节点时缺少主机名与 IP 地址的重复校验。
- 目标：在服务器节点页面提供“测试全部节点”能力，并在保存节点配置前校验主机名和 IP 地址在同一集群内唯一。
- 实施要求：
  - “测试全部节点”应覆盖当前集群配置中的全部服务器节点，复用现有单节点测试逻辑，并展示每个节点独立的测试结果与失败原因。
  - 批量测试过程中，单个节点失败不得中断其他节点的测试；应避免对同一节点重复并发发起测试请求。
  - 新增或编辑节点时，应分别校验主机名和 IP 地址是否与该集群的其他节点重复；编辑当前节点时应排除其自身。
  - 重复校验应在前端提供即时提示，并由后端在保存接口再次校验，避免绕过前端或并发提交导致重复数据。
  - 校验失败时不得保存配置，并明确指出重复的字段及冲突节点信息；IP 地址比较应采用规范化后的值，避免因格式差异造成漏判。
- 验收方向：可一键测试集群内全部服务器节点并查看逐节点结果；任意新增或编辑操作均不能在同一集群中保存重复的主机名或 IP 地址，且并发请求下仍保持数据唯一性。

### 3.4 Kubemate 组件安装开关简化

- 当前情况：Kubemate 组件页面同时提供“启用 Kubemate 组件安装”总开关和下方各组件选项卡开关，存在重复控制入口。
- 目标：移除“启用 Kubemate 组件安装”总开关，组件是否安装仅由各选项卡中的开关决定。
- 实施要求：移除总开关对应的前端展示、状态字段、接口参数及安装计划判断；保留各组件选项卡开关的现有配置能力和依赖校验逻辑。
- 验收方向：页面不再展示总开关；任一组件选项卡开启后即可按既有规则纳入安装计划，全部组件关闭时不安装任何 Kubemate 组件。

### 3.5 NFS 挂载幂等与防卡死处理

- 当前情况：部署 NFS 后重复执行挂载脚本时，可能对已挂载的目标目录再次执行挂载操作，存在阻塞或系统卡死风险。
- 目标：使 NFS 挂载脚本具备幂等性，已正确挂载的目录不再重复挂载。
- 实施要求：
  - 执行挂载前，使用可靠的系统挂载信息检查目标目录是否已挂载。
  - 已挂载且挂载源与类型符合预期时，记录日志并跳过挂载操作。
  - 已挂载但挂载源或类型不符合预期时，明确报错并中止当前节点的挂载步骤；不得直接覆盖、卸载或重复挂载。
  - 未挂载时才执行挂载命令，并检查命令退出码及挂载后的实际状态。
  - 挂载相关日志应包含节点、目标目录和处理结果，不得泄露敏感认证信息。
- 验收方向：重复执行 NFS 部署或挂载步骤不会对已正确挂载的目录再次发起挂载；配置冲突可被明确识别并安全失败，系统不会因重复挂载而卡死。

### 3.6 Kubemate 组件组安装隔离

- 当前情况：Kubemate 组件安装流程中，一个组件或组件组安装失败可能导致后续无直接依赖关系的组件组无法继续执行。
- 目标：使各 Kubemate 组件组的安装任务相互独立，单个组件组失败时不阻塞其他可执行组件组的安装流程。
- 实施要求：
  - 安装计划应按组件组拆分独立的执行单元，并仅在存在明确依赖关系时建立前置约束。
  - 某组件组安装失败时，应记录失败状态、失败原因和必要的诊断信息，并继续执行不依赖该组件组的其他已启用组件组。
  - 依赖失败组件组的后续任务应标记为“已跳过”或等价状态，并明确显示阻塞原因；不得将其误报为安装失败或安装成功。
  - 单个组件组的重试、取消和状态查询不得影响其他组件组已完成、执行中或待执行的任务。
  - 安装结果应按组件组汇总展示成功、失败和跳过状态，便于针对失败组件组单独处理。
- 验收方向：任一组件组故意安装失败后，其他无依赖且已启用的组件组仍可完成安装；存在依赖关系的组件组可被正确跳过并说明原因，整体任务状态与各组件组实际执行结果一致。

### 3.7 集群安装详情按任务 ID 展示

- 当前情况：同一集群可能多次发起安装任务，安装详情页面无法清晰区分不同任务 ID 对应的安装过程。
- 目标：集群安装详情页面按任务 ID 展示各次安装过程，支持查看当前任务及历史任务的独立执行记录。
- 实施要求：
  - 页面应展示该集群关联的安装任务列表，并明确显示任务 ID、任务状态、创建时间、开始时间和结束时间。
  - 用户选择任务 ID 后，安装阶段、步骤状态、执行进度、日志和错误信息必须全部切换到该任务的数据，不得混合不同任务的执行记录。
  - 默认优先展示正在执行的任务；不存在执行中任务时，默认展示最近创建的任务。
  - 页面刷新或通过包含任务 ID 的链接直接访问时，应保持当前选中的任务，并正确恢复其安装详情。
  - 任务执行期间仅更新当前任务对应的数据；新任务创建后不得覆盖或篡改历史任务记录。
  - 查询不到指定任务、任务不属于当前集群或任务数据已失效时，应展示明确的空状态或错误提示，并允许用户切换至其他有效任务。
- 验收方向：同一集群存在多个安装任务时，可按任务 ID 切换并查看各自完整、独立的安装过程；刷新页面后仍保持选中任务，任意任务的状态、进度和日志均不会串入其他任务。
